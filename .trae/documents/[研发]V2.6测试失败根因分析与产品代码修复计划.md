# [研发] V2.6 测试失败根因分析与产品代码修复计划

## 结论

**核心根因已定位**：`RepositoryImpl` 中 25+ 处调用 `store.executeSql()` 返回 `Promise<void>`（异步），但代码未使用 `await`，导致 UPDATE/DELETE 操作未执行完毕即被后续读操作读取，造成数据不一致。此外 `rowToPerson`/`rowToStory` 中 `rs.getLong()` 对 NULL 列返回 0 而非 null，导致可空字段始终为默认值。

## Bug 1（P0）：`executeSql` → `executeSync`

### 根因

SDK 声明 `executeSql(sql, bindArgs?): Promise<void>`（API 9+），是**异步方法**。`RepositoryImpl` 中 25+ 处调用均未 `await`，SQL 未执行完毕即被后续 `querySqlSync`/`getPerson`/`getStory` 读取。

### 影响范围

- `updatePerson`：字段更新不生效（birthday/gender/remark/personType/avatarBlob）
- `updateStory`/`updateStoryAll`：字段更新不生效
- `unlinkPersonStory`：unlink 后 isLinked 仍返回 true
- `deletePerson`/`deleteStory`：级联删除不执行
- `addPhotoForOwner`：reference_count/photo_count 不更新
- `removePhotoForOwner`：reference_count/photo_count 不回退
- `gcOrphanPhotoRefs`：误删有引用的 photo
- `updatePhotoRefStatus`：状态不更新
- `ensureSchemaV1`：DDL 建表（因 beforeAll 中有延迟，暂未暴露问题）

### 修复方案

将所有 `store.executeSql(sql, bindArgs)` 替换为 `store.executeSync(sql, args)`。

**API 签名对比**：
```typescript
// 旧（异步，返回 Promise）
executeSql(sql: string, bindArgs?: Array<ValueType>): Promise<void>;

// 新（同步，返回 ValueType，API 12+）
executeSync(sql: string, args?: Array<ValueType>): ValueType;
```

**涉及文件**：`entry/src/main/ets/infrastructure/repository/RepositoryImpl.ets`

**具体替换点**（约 25 处）：

| 方法 | 行号范围 | SQL 语句 |
|------|----------|----------|
| `updatePerson` | ~244 | `UPDATE person SET ...` |
| `updateStory` | ~324 | `UPDATE story SET ...` |
| `updateStoryAll` | ~366 | `UPDATE story SET ...` |
| `unlinkPersonStory` | ~415 | `DELETE FROM person_story ...` |
| `linkPersonStory` | ~425 | `INSERT OR IGNORE INTO person_story ...` |
| `deletePerson` | ~628-637 | `DELETE FROM photo_owner_link ...` + `DELETE FROM person_story ...` + `UPDATE photo_ref ...` + `DELETE FROM person ...` |
| `deleteStory` | ~665-674 | `DELETE FROM photo_owner_link ...` + `DELETE FROM person_story ...` + `UPDATE photo_ref ...` + `DELETE FROM story ...` |
| `addPhotoForOwner` | ~588-598 | `UPDATE photo_ref SET reference_count ...` + `UPDATE story/person SET photo_count ...` |
| `removePhotoForOwner` | ~708-726 | `UPDATE photo_ref SET reference_count ...` + `UPDATE story/person SET photo_count ...` |
| `gcOrphanPhotoRefs` | ~763 | `DELETE FROM photo_ref ...` |
| `updatePhotoRefStatus` | ~739 | `UPDATE photo_ref SET ...` |
| `ensureSchemaV1` | ~40-80 | 多条 CREATE TABLE / INSERT |

### 注意事项

1. `executeSync` 返回 `ValueType`，对于 DML 语句可能返回受影响行数。可利用此返回值替代 `changesCount`。
2. `ensureSchemaV1` 中的 DDL 语句也需替换，保持一致性。
3. 事务内多条 `executeSync` 调用是同步的，`commit()` 后数据立即可见。

## Bug 2（P0）：`rowToPerson`/`rowToStory` NULL 检测

### 根因

`ResultSet.getLong()` 对 NULL 列返回 `0`（而非 `null`），`ResultSet.getBlob()` 对 NULL 列可能返回空 `Uint8Array`（而非 `null`）。代码直接使用 `getLong` 返回值判断，导致可空字段始终为默认值。

### 影响范围

- `birthday`：始终为 `number`（0 代表 NULL），无法区分"未设置"和"1970-01-01"
- `gender`：始终为 `number`（0 = MALE），无法区分"未设置"和"MALE"
- `avatarBlob`：可能为空 `Uint8Array` 而非 `null`
- `timeStart`/`timeEnd`（Story）：同 birthday 问题
- `description`/`location`/`coverUri`（Story）：`getString` 对 NULL 可能返回 `''`

### 修复方案

使用 `rs.isColumnNull(columnIndex)` 在读取前检查 NULL。

**API 签名**：
```typescript
isColumnNull(columnIndex: number): boolean;  // API 12+
```

**涉及文件**：`entry/src/main/ets/infrastructure/repository/RepositoryImpl.ets`

**具体修改**：

`rowToPerson` 方法中：
```typescript
// 修改前
const birthdayRaw = rs.getLong(rs.getColumnIndex('birthday'));
// ...
birthday: birthdayRaw !== null ? Number(birthdayRaw) : null,

// 修改后
const birthdayIdx = rs.getColumnIndex('birthday');
const birthday: number | null = rs.isColumnNull(birthdayIdx) ? null : rs.getLong(birthdayIdx);
```

同理修改 `gender`、`avatarBlob`、`timeStart`、`timeEnd`、`description`、`location`、`coverUri` 等可空字段。

## Bug 3（P1）：`updatePerson`/`updateStory` 对不存在行返回 true

### 根因

`updatePerson`/`updateStory` 在 `executeSql` 后无条件返回 `true`，即使 WHERE 条件未匹配任何行。

### 修复方案

利用 `executeSync` 的返回值（对 DML 可能返回受影响行数），或改用 `changesCount` 验证。

```typescript
// 修改前
store.executeSql(`UPDATE person SET ... WHERE id = ?;`, bindArgs);
return true;

// 修改后
const result = store.executeSync(`UPDATE person SET ... WHERE id = ?;`, bindArgs);
return typeof result === 'number' && result > 0;
```

如果 `executeSync` 对 DML 不返回行数，则使用 `changesCount`：
```typescript
store.executeSync(`UPDATE person SET ... WHERE id = ?;`, bindArgs);
return changesCount(store) > 0;
```

## Bug 4（P1）：`deletePerson`/`deleteStory` 的 `changesCount` 问题

### 根因

当前 `deletePerson`/`deleteStory` 在事务内执行多条 DELETE，`commit()` 后调用 `changesCount(store)` 检查。但 `changes()` 函数只返回最近一条 DML 的影响行数，且在 `commit()` 后可能被重置。

### 修复方案

在 `executeSync` 替换后，`changesCount` 应能正确工作（因为同步执行）。如果仍有问题，改用验证式检查：

```typescript
// 修改后
store.executeSync('DELETE FROM person WHERE id = ?;', [id]);
store.commit();
// 验证删除成功
return this.getPerson(id) === null;
```

## Bug 5（P2）：Migration 测试版本号不匹配

### 根因

`ensureSchemaV1` 对新数据库设置版本为 `RDB_SCHEMA_META_VERSION`（5），但 Migration 测试期望版本从 1 开始逐步递增。

### 修复方案

更新 `MigrationTier2.test.ets` 中的测试用例：

1. 不使用 `ensureSchemaV1`（它创建完整 schema 并设版本为 5）
2. 改为手动创建 v1 基础表，设置版本为 1
3. 然后运行 MigrationRunner 从 1 → 5

或者，如果测试目的是验证"已处于最新版本的数据库不受迁移影响"，则调整期望值为 5。
